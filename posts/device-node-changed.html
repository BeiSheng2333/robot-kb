重启后 /dev/ttyUSB0 变成 ttyUSB1：设备命名治理

这是“昨天还好好的”最典型的原因之一。设备名不是身份，只是内核分配的序号，必须换成稳定的名字。

更新 2026-11-11 约 8 分钟 硬件与外设

现象：设备昨天还能正常跑，今天上电后底盘没反应、激光连不上。翻日志发现程序在打开 /dev/ttyUSB0，但那块设备今天变成了 /dev/ttyUSB1，而 ttyUSB0 现在是另一块 USB 设备。

根因不复杂：/dev/ttyUSB* 是按 USB 枚举顺序分配的，谁先被系统识别谁就是 0。这个顺序会随上电时序、USB 口位置、HUB 供电状态变化。

先看清设备到底是谁

# 当前 USB 设备树
lsusb -t

# 已存在的稳定软链接（最省事的方案）
ls -l /dev/serial/by-id/
ls -l /dev/serial/by-path/

# 查看某个 tty 的完整属性
udevadm info -a -n /dev/ttyUSB0 | grep -E "looking at|idVendor|idProduct|serial"

如果 /dev/serial/by-id/ 里已经能看到带序列号的路径，那你甚至不需要写规则，直接把程序配置成使用该路径即可。

优先选择

能用 by-id 就不要用 by-path。前者跟随设备芯片序列号，换 USB 口也稳定；后者跟随物理端口，换口就失效。

用 udev 规则起可读的名字

当设备没有唯一序列号（很多廉价 CH340 模块），或者你想让配置更语义化，就写规则：

# /etc/udev/rules.d/99-robot-serial.rules
# 有序列号：按 idVendor + idProduct + serial 绑定
SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ATTRS{idProduct}=="6001", \
  ATTRS{serial}=="A1B2C3D4", SYMLINK+="robot/chassis", MODE="0666", GROUP="dialout"

# 无序列号：按固定 USB 物理端口绑定
SUBSYSTEM=="tty", KERNELS=="1-2.3", SYMLINK+="robot/lidar", MODE="0666", GROUP="dialout"

规则名建议以 99- 开头，避免被更早的规则覆盖。写完重新加载：

sudo udevadm control --reload-rules
sudo udevadm trigger
ls -l /dev/robot/

之后程序统一使用 /dev/robot/chassis 和 /dev/robot/lidar，与枚举顺序彻底解耦。

权限：别用 sudo 跑业务

现场常见做法是给设备 chmod 666，方便但不够安全。更稳妥的是把运行用户加入 dialout 组，并在规则里指定 GROUP="dialout"：

sudo usermod -aG dialout robot
# 重新登录或重启后生效
id robot

上电时序：设备还没就绪就启动了

即使名字稳定，也可能出现“程序启动时设备还不存在”。尤其在工控机上，USB 设备枚举比系统服务启动慢。两种处理：

  1. 启动脚本等待设备在拉起业务前轮询节点是否存在，超时再报错退出。
  2. systemd 依赖设备单元使用 After= 关联对应的 .device 单元，让系统保证顺序。
# 启动脚本中的等待逻辑
for i in $(seq 1 50); do
  [ -e /dev/robot/chassis ] && break
  sleep 0.2
done
[ -e /dev/robot/chassis ] || { echo "chassis device not ready"; exit 1; }
注意

不要用 sleep 10 这类固定延时。它在快机器上浪费十秒，在慢机器上依然可能不够，而且掩盖了真正的问题。

验证与固化

改完必须做一次完整的断电重启验证，而不是热插拔：

  • 冷启动 3 次，检查 /dev/robot/ 下节点是否都出现；
  • 拔掉再插上同一设备，确认名字不变；
  • 交换两个 USB 口，确认 by-id 方案依然正确；
  • 把规则文件、设备对应表纳入版本管理，写进交付文档。
交付建议

在设备档案里维护一张“物理设备 ↔ 稳定节点名 ↔ 用途”对照表。以后换件、维修、远程支持都能少问好几轮。
