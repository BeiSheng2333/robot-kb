ROS 2 通信超时与丢包的逐层排查

通信问题最麻烦的地方是：它时好时坏。所以不要试图一次解释全部现象，先用命令把范围一层层收窄。

“话题收不到数据”在 ROS 2 里至少有五种完全不同的原因：网络丢了、发现没建起来、QoS 不匹配、消息太大传不过去、或者发布端根本就没在发。它们的现象很像，处理方式却完全不同。

先分清三种现象

现象典型表现优先怀疑
完全收不到ros2 topic list 里看不到，或能看到但永久无数据发现机制、Domain ID、QoS
偶发丢失有数据，但频率低于预期，时间轴上有空洞无线丢包、大消息分片
延迟抖动平均延迟正常，但 P99 很高，偶尔卡顿网络拥塞、CPU 抢占、序列化开销

第 0 步：固定基线

先确认三件事，否则后面所有结论都不可信：

# 中间件实现，必须两端一致
echo $RMW_IMPLEMENTATION

# 域 ID，跨网段多套系统时最容易撞
echo $ROS_DOMAIN_ID

# 本地回环是否正常
ros2 run demo_nodes_cpp talker  # 窗口 A
ros2 run demo_nodes_cpp listener # 窗口 B

如果本机 demo 都收不到，问题不在业务代码，而在环境变量或中间件安装。先修这里。

网络层：先证明链路是干净的

不要用一次 ping 就下结论，看的是分布，不是平均值。

# 连续 1000 包，观察丢包与抖动
ping -i 0.2 -c 1000 192.168.1.10

# 探测 MTU 是否被截断（不要分片）
ping -M do -s 1400 -c 5 192.168.1.10

# 无线链路质量
iw dev wlan0 link
现场高频原因

车端连的是 2.4G 且与现场其他设备同信道；AP 漫游时重关联耗时过长；交换机端口协商成半双工。这三类都会表现为“偶发丢包”，但和 ROS 2 本身没有任何关系。

中间件层：发现机制是否建立

ROS 2 默认依赖多播做节点发现。很多企业网络和无线 AP 会屏蔽多播，于是表现为“进程都活着，但互相看不见”。

# 查看参与者与端点信息
ros2 node list
ros2 topic info /scan --verbose

# 综合诊断
ros2 doctor --report

如果 topic list 里根本没有目标话题，先检查发现：临时把两端接同一台交换机、关闭防火墙、或显式配置单播 peers，再观察是否恢复。恢复即说明是多播被阻断。

QoS 层：最隐蔽的不匹配

ROS 2 的 QoS 不兼容不会报错，只会安静地收不到。典型组合：

发布端订阅端结果
reliablebest_effort可以通信
best_effortreliable无法建立，收不到
transient_localvolatile能收到新消息，拿不到历史
volatiletransient_local无法建立

传感器话题（激光、图像）通常是 best_effort，而业务代码里手写的订阅者默认是 reliable。这一条能解释大量“我明明订阅了却收不到”的问题。

大消息：图像与点云的专属问题

超过 MTU 的消息需要分片重组。无线环境下分片丢失会导致整帧丢弃，表现为“帧率上不去、偶尔整段缺失”。

  • 优先降低分辨率或频率，而不是盲目加大缓冲区；
  • 在车端内部节点之间启用共享内存传输，减少网络拷贝；
  • 跨机传输考虑压缩或按需拉流，不要把原始点云直接推给调度端；
  • 确认发布端没有在单线程里同时做重计算，导致实际发布频率低于配置值。

时间与结论

最后别忘了时间。ros2 topic hz 显示正常、TF 却报 extrapolation 错误，通常是系统时钟被 NTP 大幅校正过。检查方法：

timedatectl status
chronyc tracking
收尾清单

两端 RMW 与 Domain 一致 → ping 分布干净 → 节点互相可见 → QoS 组合兼容 → 消息大小合理 → 时钟稳定。六步都过，再回去看业务代码。
